# Code Review

지정된 코드 또는 이번 작업에서 작성·수정한 코드를 검토하고 품질 문제를 개선한다. PR 유무와 관계없이 구현 후 자기 리뷰에 적용한다. PR 자체의 분석과 피드백 문서가 주목적인 요청은 `pr-review`로 처리한다.

## Invocation and Self-Review

* 명시적인 리뷰 요청뿐 아니라 코드를 작성하거나 수정한 개발 작업에도 적용한다. 구현을 마친 뒤 최종 완료 보고·커밋·PR 생성 전에 이 스킬을 읽고 자기 리뷰를 수행한다.
* 매 편집마다 호출하지 않고 하나의 논리적인 구현 단위가 끝났을 때 수행한다. 코드 변경이 없는 질문 답변, 조사, 문서 편집만으로는 구현 후 자기 리뷰를 시작하지 않는다.
* 명시적인 코드 리뷰 요청에서는 지정된 파일·diff·범위를 검토한다. 구현 후 자기 리뷰에서는 이번 작업의 diff와 새 파일을 검토한다. 기존 사용자 변경을 이번 구현과 구분하고, 변경된 코드의 호출부·주변 코드·관련 테스트까지 확인한다.
* 작성 당시의 의도만으로 정당화하지 말고 실제 코드와 요구사항을 다시 대조한다. 자기 리뷰를 독립 리뷰나 실제 실행 QA가 완료된 것으로 표현하지 않는다.
* 검토 중 발견한 문제는 코드 수정으로 해결할 수 있다. 구현 후 자기 리뷰에서는 승인된 작업 범위 안의 명백한 버그와 동작·계약을 보존하는 단순화·가독성 개선을 직접 반영한다. 사용자가 분석만 요청한 경우에는 그 요청을 따른다. 새 요구사항, 중요한 설계 선택이나 범위 확대가 필요하면 이유와 대안을 제안한다.
* 리뷰에 따른 코드 수정이 있으면 영향받은 검증을 수행하고 수정된 diff를 다시 리뷰한다. 실질적인 발견사항이 해소되거나 미해결 사유가 정리되면 종료하며, 취향성 변경으로 반복하지 않는다.
* 이 절차는 스킬 선택과 실행에 관한 지침이다. 파일 저장 이벤트를 감지하는 실행 훅이나 매 호출을 보장하는 자동화가 설치된 것으로 설명하지 않는다.

## Guidelines

* 변경사항과 목적을 파악하고 개발자가 이해하기 쉽게 설명한다.
* 기존 프로젝트의 아키텍처, 구조, 패턴, 컨벤션을 유지하고 있는지 확인한다.
* 변경 목적과 관계없는 불필요한 변경이 포함되어 있는지 확인한다.
* 변경 범위가 필요 이상으로 다른 도메인이나 책임까지 확장되어 있는지 확인한다.
* 코드가 불필요하게 복잡하게 작성되었는지 검토하여 simplicity를 확보한다. 동일한 동작과 계약을 유지하면서 더 단순하게 표현할 수 있는지 확인한다.
* 코드가 가독성 좋게 작성되어 있는지 확인한다. 이름, 함수 길이, 중첩, 조건식과 실행 흐름을 독자가 쉽게 이해할 수 있는지 검토한다.
* 코드가 명확하게 작성되어 있는지 확인한다. 책임, 입력·출력, 상태 변화, 부작용과 오류 처리의 의미가 드러나는지 검토한다.
* 각 코드가 정말로 이번 변경에 필요한 코드인지 검토한다. 새 분기·헬퍼·추상화·설정·의존성·테스트를 현재 요구사항 또는 유지해야 할 기존 계약과 연결할 수 있는지 확인한다.
* 코드, 설계, 동작, 구조 측면에서 개발자가 확인해야 할 리뷰 항목을 찾는다.
* 리뷰 항목에 적절한 해결 방법이 있다면 권장안을 설명하고, 필요한 경우 다른 대안과 차이점도 함께 제시한다.
* 각 리뷰 항목에 번호를 붙여 추가 지시하기 편하게 한다.
* 일반적인 모범 사례를 일괄 적용하기보다 기존 프로젝트의 구조와 맥락을 기준으로 판단한다.
* 각 리뷰 항목에 중요성에 따라 [P1~P3] 태그를 붙인다.
* 미해결 항목의 코드 위치가 명확하면 해당 위치에 앱 내 인라인 리뷰로 표시하고, 전반적인 의견은 본문에 작성한다. 수정한 항목은 결과 보고에 해결 여부를 구분한다.

## AI-Slop Review

AI-Slop은 작성자가 AI인지 추측하는 분류가 아니라, 그럴듯해 보이지만 불필요한 복잡성이나 결함을 추가하는 코드 패턴을 점검하기 위한 기준으로 사용한다. 다음 항목은 변경된 코드에 적용한다.

* **과잉 추상화와 미래 대비:** 실제 요구가 없는 팩토리, 래퍼, 전략 계층, 확장 지점이나 설정을 찾아 더 직접적인 구현을 검토한다. 사용처가 하나라는 이유만으로 추상화를 제거하지 말고 책임 분리와 테스트 경계를 고려한다.
* **중복과 패턴 이탈:** 기존 헬퍼를 다시 구현하거나 유사한 로직을 복사했는지, 프로젝트의 기존 오류 처리·데이터 접근·상태 관리 방식과 불필요하게 달라졌는지 확인한다. 우연히 비슷한 서로 다른 도메인 로직까지 강제로 합치지 않는다.
* **과잉 방어와 실패 은폐:** 계약상 불가능한 조건의 반복 검사, 근거 없는 재시도, 오류를 삼키는 catch, 실패를 성공처럼 보이게 하는 기본값을 검토한다. 외부 입력 검증, 보안 경계, 실제 장애 대응과 호환성 보장은 유지한다.
* **장식성 코드:** 코드 동작을 그대로 반복하는 주석, 정보 없는 로그, 모호한 이름, 사용되지 않는 코드나 의존성을 확인한다. 판단 이유·계약·운영 진단에 필요한 설명과 로그는 보존한다.
* **복잡한 실행 흐름:** 큰 함수, 깊은 중첩, 중복 분기, 숨겨진 부작용 때문에 핵심 동작을 추적하기 어려운지 확인한다. 줄 수 감소보다 의미와 동작을 쉽게 읽을 수 있는 구조를 우선한다.
* **근거 없는 구현:** 사용한 API·옵션·타입이 실제 설치 버전과 맞는지, TODO·더미 구현·하드코딩된 성공 응답으로 요구사항을 충족한 것처럼 보이게 하지 않았는지 확인한다. 의심되는 부분은 코드·공식 문서·검증 결과로 확인한다.
* **검증의 빈틈:** 테스트가 실제 요구 동작과 의미 있는 실패 경로를 확인하는지 검토한다. 구현을 그대로 복제한 기대값, 핵심 경로를 모두 대체한 mock, 통과만을 위한 검증 완화가 문제를 숨기는지 확인한다. 작은 변경마다 불필요한 테스트 추가를 요구하지 않는다.

발견사항에는 구체적인 코드 위치, 어떤 요구나 계약에 영향을 주는지, 유지보수·동작상의 비용과 더 단순한 대안을 제시한다. 실제 근거 없이 “AI 같다”거나 개인 취향만으로 결함을 단정하지 않는다. 컴파일·테스트 통과만으로 위 항목을 통과했다고 판단하지 않는다.

### Research Sources

2026-10-04에 다음 자료를 확인하고 프로젝트 맥락에 맞는 검토 기준으로 재구성했다. 통계나 특정 도구의 결과를 모든 AI 코드에 일반화하지 않는다.

* [Slop Guard](https://github.com/trisouro/slop-guard): 실무 규칙 모음의 과잉 추상화, 방어적 과잉 설계, 불필요한 주석·의존성과 범위 확대 사례를 참고했다. 커뮤니티 지침이며 보편적인 판정 표준은 아니다.
* [Beyond Functional Correctness: Design Issues in AI IDE-Generated Large-Scale Projects](https://arxiv.org/abs/2604.06373): Cursor로 생성한 10개 프로젝트에서 관찰한 중복, 복잡성, 큰 함수와 예외 처리 문제를 참고했다. 특정 연구 조건의 결과이며 모든 생성 코드의 특성을 입증하지 않는다.
* [GitHub: Code review in the age of AI](https://github.blog/ai-and-ml/generative-ai/code-review-in-the-age-of-ai-why-developers-will-always-own-the-merge-button/): 구현 후 자기 리뷰, 기존 패턴과의 일관성, 테스트와 자동 검사 유지에 관한 지침을 참고했다. 자기 리뷰는 기존 QA와 사람의 판단을 대체하지 않는다.

## Output

분석 결과를 보기 쉬운 Markdown 문서로 정리하여 `.md` 파일로 저장한다. 기존 리뷰 문서가 있으면 갱신하고, 프로젝트에서 지정한 문서 위치가 있으면 따른다. 별도 지정이 없으면 작업 공간의 적절한 산출물 위치에 저장한다.

문서에는 변경 규모에 따라 다음 내용을 포함한다.

* 검토 대상 코드 또는 로컬 변경의 목적과 주요 변경사항
* 주요 구현 내용과 영향 범위
* 기존 아키텍처 및 컨벤션과의 일관성
* 단순성, 가독성, 명확성, 코드의 필요성과 AI-Slop 검토 결과
* 불필요하거나 과도하게 확장된 변경사항
* 개발자가 확인해야 할 리뷰 항목
* 리뷰 항목에 대한 권장 해결안 및 대안
* 직접 반영한 수정과 남은 리뷰 항목, 필요한 경우 개발자가 이해하기 쉬운 리뷰 메시지
* 자기 리뷰 여부, 실제 검토 범위, 실행한 검증과 미검증 영역, 미해결 항목

고정된 형식을 강제하지 않고 변경 규모와 구조에 맞게 문서를 구성한다. 발견사항이 없으면 “검토 범위 내 발견사항 없음”으로 적고, 검증하지 않은 동작까지 보장하지 않는다.
