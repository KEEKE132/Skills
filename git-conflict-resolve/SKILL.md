# Git Merge Conflict

PR의 대상 브랜치와 원본 브랜치 사이에 merge conflict가 발생했을 때 이를 분석하고 해결한다.

Skill 사용 시 다음 정보가 주어진다.

* **Target Branch (A)**: PR이 merge될 대상 브랜치
* **Source Branch (B)**: PR 변경사항이 있는 원본 브랜치

PR 방향은 `B → A`이다.

충돌 해결을 위해 A의 변경사항을 B에 반영하여 충돌을 해결하고, 기존 PR이 다시 merge 가능한 상태가 되도록 한다.

## Workflow

### 1. 상황 파악

작업을 시작하기 전에 다음을 확인한다.

* 대상 브랜치 A
* 원본 브랜치 B
* 현재 브랜치와 Git 상태
* A와 B의 변경사항 및 PR의 목적

필요한 최신 변경사항을 가져오고, A를 B에 반영하는 과정에서 발생하는 conflict를 확인한다.

구체적인 Git 명령과 작업 방식은 현재 repository와 Git 상태에 맞게 판단한다.

### 2. Conflict 분석

충돌이 발생하면 바로 수정하지 않는다.

먼저 각 conflict에 대해 다음을 파악한다.

* 충돌한 코드
* A에서 변경된 내용과 의도
* B에서 변경된 내용과 의도
* 두 변경사항이 충돌한 이유
* 해결 방식에 따라 달라질 수 있는 동작

필요하다면 주변 코드와 관련 구현까지 확인하여 변경사항의 맥락을 파악한다.

### 3. 개발자에게 설명

각 conflict를 개발자가 판단할 수 있도록 이해하기 쉽게 설명한다.

가능하면 다음 내용을 포함한다.

* 어떤 충돌이 발생했는지
* A와 B가 각각 무엇을 변경했는지
* 왜 충돌하는지
* 해결 시 고려해야 할 사항

### 4. 해결안 제안

각 conflict에 대해 합리적인 해결 방법을 제안한다.
이때 각 conflict에 번호를 붙여 개발자가 지시하기 편하게 한다.

여러 방법이 가능하다면 주요 대안을 제시하고 각각의 특징과 장단점을 설명한다.

예를 들어 다음과 같은 방향이 있을 수 있다.

* A의 변경을 기준으로 B를 조정
* B의 변경을 유지하면서 A의 변경을 반영
* 양쪽 변경 의도를 통합

실제로 의미 있는 선택지만 제시하고 억지로 여러 대안을 만들지 않는다.

각 conflict마다 AI가 가장 적절하다고 판단하는 **권장안과 이유**를 함께 제시한다.
이때 각 충돌에 대한 내용과 그 해결안들의 특징들을 보기 쉽게 정리하여 md문서로 제공한다.

### 5. 개발자의 결정

의미 있는 판단이 필요한 conflict는 개발자의 선택이나 지시를 받은 뒤 수정한다.

개발자가 여러 conflict에 대해 한꺼번에 판단할 수 있도록 필요한 내용을 먼저 정리해서 제시할 수 있다.

개발자의 결정이 완료되면 해당 방향에 따라 conflict를 해결한다.

### 6. Merge 완료

모든 conflict를 해결한 뒤 전체 변경사항을 확인하고 필요한 검증을 수행한다.

문제가 없다면 merge 작업을 완료하고 Source Branch B에 결과를 반영하여 기존 PR이 merge 가능한 상태가 되도록 한다.
이 모든 merge는 로컬 브랜치에서 진행하며 머지 이후 푸시는 진행하지 않는다.

작업 방식과 검증 범위는 프로젝트와 변경사항에 맞게 판단한다.

## Guidelines

* PR 방향 `B → A`와 conflict 해결을 위한 변경 반영 방향 `A → B`를 혼동하지 않는다.
* conflict를 이해하기 전에 임의로 코드를 수정하지 않는다.
* A 또는 B 중 한쪽의 변경을 무조건 우선하지 않는다.
* 리뷰 대상 코드뿐 아니라 필요한 경우 프로젝트 맥락을 함께 확인한다.
* 해결 방법이 여러 개라면 개발자가 판단할 수 있는 정보를 제공한다.
* 개발자가 선택한 해결 방향을 존중한다.
* conflict 해결과 직접 관련 없는 변경은 불필요하게 포함하지 않는다.
* 불확실한 부분은 추측해서 결정하지 말고 개발자가 판단할 수 있도록 설명한다.

## Result

작업 완료 후 다음 내용을 간단히 정리한다.

* 발생한 주요 conflict
* 적용한 해결 방식
* 주요 변경사항
* 수행한 검증
* merge 완료 여부
