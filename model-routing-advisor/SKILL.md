# 모델 라우팅 어드바이저

사용자의 작업을 대신 설계하거나 불필요하게 멈추게 하지 않으면서, **작업 난이도와 필요한 결과 품질에 맞는 모델·추론수준**을 제안한다. 정확성뿐 아니라 완성도, 설계의 일관성, 유지보수성, 표현·시각 품질 등 해당 산출물에 필요한 기준을 반영한다. 비용·속도는 명시된 제약 안에서 고려하되, 사용자가 요구하지 않은 최저 비용을 최우선 목표로 삼지 않는다.

권고는 강제가 아니다. 사용자가 지정한 구성으로 실행할 권한과, 그 구성이 작업에 가장 적합하다는 평가는 구분한다. 이미 선택됐다는 사실은 추천 근거가 아니다.

## 현재 설정과 독립적으로 추천하기

다음 순서로 판단한다. 현재 설정은 마지막 비교에서만 사용한다.

1. **작업 요구를 먼저 정리한다.** 단계, 핵심 판단의 난이도, 산출물의 품질 기준, 실패 비용, 탐색·검증 범위, 명시된 비용·시간 제약을 파악한다. 실행 중인 모델 이름, 선택된 추론수준, 이전 추천을 작업 난이도의 증거로 사용하지 않는다.
2. **실제 후보와 특성을 확인한다.** 환경에서 확인된 모델·버전과 지원 추론수준을 사용한다. 현재 모델만 보인다고 그것만 후보로 취급하지 않는다. 선택지나 비교 근거가 부족하면 그 한계를 밝히고 조건부로 추천한다. 모델별 작업 적합성 판단에 근거가 필요하면 [모델 비교 근거](references/model-fit.md)를 읽고 최신 공식 자료 또는 같은 조건의 평가로 확인한다. 스스로 해당 모델이라는 사실은 성능 근거가 아니다.
3. **작업에 맞는 후보들을 비교한다.** 선택지가 여러 개라면 유력 후보와 가장 관련 있는 대안을 검토한다. 각 후보의 예상 품질, 놓치기 쉬운 요구, 검증·수정 부담을 비교한다. 특정 모델 계열이나 Medium·High를 출발점으로 고정하지 않는다. 모델과 추론수준은 별도로 판단하되, 조합 전체가 필요한 품질을 충족하는지 확인한다.
4. **추천을 정한다.** 필요한 품질을 신뢰성 있게 충족하고 검토·재작업 부담까지 고려해 적합한 구성을 고른다. 더 강한 구성의 품질 이점이 실질적이면 반영하고, 더 가벼운 구성도 동등하게 충족한다면 비용·속도를 비교한다. 우열을 확인하지 못했으면 미확인이라고 밝힌다. 비교가 불확실하다는 이유로 현재 구성이나 더 낮은 구성을 자동 선택하지 않는다. 실제로 평가하지 않은 후보의 실패, 점수, 속도·비용 차이를 만들어내지 않는다.
5. **마지막에 현재 설정과 비교한다.** 현재 설정을 알 때만 유지·상향·하향·모델 변경 관계를 덧붙인다. 전환 수고나 사용자의 실행 선택 때문에 작업 기준의 추천을 현재 설정에 맞춰 바꾸지 않는다. 현재 설정을 모르면 추측하지 않고 추천은 계속한다.

응답 전에 반대 조건으로 점검한다. **작업, 품질 요구, 제약, 선택지, 비교 근거가 같고 현재 설정만 Sol↔Terra 또는 Medium↔High로 달라져도 같은 추천이 나오는가?** 현재 설정을 가렸을 때 결론이 달라지면 작업 근거부터 다시 비교한다. 같은 근거라면 이전 추천도 새 추천의 기준점이 아니다. 최신 근거가 달라졌다면 무엇이 달라졌는지 밝힌다.

추천 이유는 작업의 구체적 요구와 관련 대안의 차이를 설명한다. “현재 모델로 충분”, “이미 High”, “일반적으로 Medium”만으로 정당화하지 않는다. 유지 추천에도 같은 기준을 적용한다. 후보들이 비슷하면 억지로 우열을 만들지 말고 잠정 추천과 가까운 대안, 차이를 확인할 항목을 짧게 밝힌다.

## 명시 호출은 추천 전용 턴

사용자가 `$model-routing-advisor`, “model router 실행”, “모델 추천 먼저” 등으로 **현재 작업의 추천을 명시 호출**하면, 이 규칙이 아래의 일반적인 Plan·Implement 진행 규칙보다 우선한다. 이 스킬 자체를 수정·설명·검토하라는 요청은 추천 전용 호출이 아니다.

응답을 시작하기 전에 **사용자 메시지와 이전 대화만으로** 라우터 단계를 정한다. 새 작업의 요구만 설명하고 실제 조사·계획·수정 결과가 아직 없다면 Pre-Plan이다. “추가해야 해”, “확장 가능한 구조를 고려해야 해” 같은 표현은 추천할 작업의 설명이지, 같은 턴에서 계획·구현을 시작하라는 승인이 아니다. Codex 앱의 Plan Mode 같은 UI 실행 모드도 라우터의 Plan 단계로 간주하지 않는다. 라우터의 Plan은 사용자가 후속 메시지로 계획을 시작하라고 지시했거나, 이전 대화에서 이미 그 작업의 실제 조사·계획이 진행된 경우다.

- 해당 응답에서는 현재 요청 단계의 모델·추론수준·Ultra 권고와 짧은 근거만 제공하고 응답을 끝낸다. 같은 메시지에 계획 수립이나 구현 요청이 함께 있어도 실행하지 않는다.
- Pre-Plan 명시 호출에서는 저장소·코드를 깊게 조사하지 않는다. Plan 명시 호출에서는 추천 근거에 필요한 읽기 전용 조사만 하고, 실제 계획 문서는 만들지 않는다. Implement 중 명시 호출은 현재 안전 경계에서 평가한 뒤 추가 수정·테스트를 진행하지 않는다.
- 권장 설정이 현재 구성과 같거나 상향 권고가 없더라도 추천 전용 턴 원칙은 같다. 같은 구성을 추천했더라도 그 응답에서 본 작업을 시작하지 않는다.
- 응답 마지막에는 재개할 다음 행동을 한 줄로 알린다. 사용자가 다음 메시지에서 `(plan)`, `(implement)` 또는 동등한 진행 지시를 보내면 현재 설정으로 재개한다. 모델 변경은 재개의 필수 조건이 아니다.

예: `$model-routing-advisor 구독 기능과 플랜별 사용량 제한을 추가해야 해. 확장 가능한 구조도 고려해 줘.` → **Pre-Plan**으로 계획용·예상 구현용 모델/추론수준과 근거를 권고하고 응답 종료. 저장소 탐색, 한도 정책 결정, 설계 질문, 계획 작성은 후속 사용자 지시 전까지 하지 않는다.

이 규칙은 사용자가 직접 router를 요청한 경우에만 적용한다. router가 묵시적으로 선택됐고 현재 설정이 충분하면 아래 일반 흐름대로 본 작업을 계속할 수 있다.

## 첫 호출 이후 같은 목표에서 계속 적용

첫 호출의 추천 전용 턴이 끝나도 **같은 대화의 같은 목표**에는 라우팅 판단을 이어간다. 사용자가 매 단계마다 스킬을 다시 호출할 필요는 없다. 후속 메시지에 스킬 이름이 없어도 이전 라우팅 결과와 현재 작업 단계를 확인하고 아래 전환을 따른다.

- 후속 `(plan)` 또는 동등한 계획 지시: 추천 전용 턴을 반복하지 말고 실제 계획을 작성한다. 계획을 마친 같은 응답 끝에서 발견사항에 근거해 **구현 모델·추론수준을 다시 추천**한다. 초기 예상과 같아도 유지 이유를 짧게 밝힌다. 그 뒤에는 사용자의 구현 지시를 기다린다.
- 후속 `(implement)` 또는 동등한 구현 지시: 별도 스킬 호출이나 모델 변경을 요구하지 않고 구현을 시작한다. 진행 중 현재 구성의 과부족을 감시하고, 실질적 불일치가 확인되면 안전 경계에서 중단해 새 구성을 추천한다.
- 후속 메시지에 `$model-routing-advisor`를 **다시 명시**했다면 그 턴은 다시 추천 전용으로 처리한다. 반대로 단계 진행 지시만 있다면 첫 호출의 추천 전용 규칙을 재적용하지 않는다.

사용자 메시지 없이 Pre-Plan → Plan → Implement를 자동으로 넘기지 않는다. 이 맥락은 같은 대화 안에서만 유지한다. 새 대화나 독립된 목표에는 이전 목표의 라우팅을 강제로 적용하지 않는다.

## 자동 호출과 재개 게이트

명시 호출뿐 아니라, 현재 설정과 요구의 격차가 실질적으로 클 때 자동으로 이 스킬을 사용한다. 자동 호출 신호는 고난도 설계 선택, 넓은 탐색 또는 검증, 요구한 결과 품질과의 격차, 고위험·비가역 변경, 긴 의존 관계를 가진 작업이며, 이 중 하나만으로 자동 호출을 강제하지 않는다. 현재 구성으로 안전하고 신뢰성 있게 진행할 수 있다면 호출하거나 중단하지 않는다. 호출 필요성을 판단할 때 현재 설정을 참고하는 것과 추천을 그 설정에 맞추는 것은 구분한다.

묵시적 호출에서 Pre-Plan 또는 Plan의 새 상향 권고를 제시하면 **권고와 handoff만** 포함하고 끝낸다. 그 응답 안에서 계획을 작성하거나 Implement로 전환하지 않는다. 추천 자체는 다음 단계 진행 승인이 아니다.

권고를 낸 뒤에는 같은 목표에 대해 대기 상태를 대화 맥락에 유지한다. 후속 사용자 메시지 없이 Plan·Implement를 자동으로 재개하지 않는다. 사용자가 `(plan)`, `(implement)` 또는 동등하게 다음 행동을 명시하면 이를 현재 설정으로 진행하라는 승인으로 간주해 위의 후속 단계에서 재개한다. 모델·추론수준 변경은 필수가 아니며, 사용자가 변경 사실을 알리면 새 설정을 반영한다.

동일 목표의 후속 단계는 최초 라우팅 판단을 이어서 적용한다. 핵심 설계, 필요한 결과 품질, 탐색 범위·검증 판단의 난도, 실패 비용, 또는 독립 병렬성에 실질적 변화가 있을 때만 다시 권고한다. 새롭고 독립된 목표는 별도로 판별한다.

## 판단 축

다음 항목은 서로 영향을 줄 수 있지만, 단일 규칙이나 점수표로 고정하지 않는다.

- **모델(Model)**: 문제 해결 능력과 작업별 강점이 필요한 품질에 맞는지 판단한다. 코드 수정, 설계, 근거 종합, 글쓰기, 시각 판단의 적합성을 구분한다. 모델 이름을 고정된 서열로 놓거나 더 높은 추론수준이 모델 간 차이를 항상 대신한다고 가정하지 않는다.
- **추론수준(Reasoning)**: 어려운 판단, 대안 비교, 탐색과 검증에 필요한 사고의 깊이와 양을 판단한다. 짧아도 어려운 설계 판단이면 높일 수 있고, 오래 걸려도 기계적 작업이나 도구 대기 중심이면 높일 필요가 없을 수 있다. 컨텍스트 창, 도구 호출 한도, 작업 시간이나 테스트 실행량을 늘리는 설정으로 설명하지 않는다.
- **병렬화와 Ultra**: 독립 작업의 분할·통합이 유효한지 별도로 판단한다. Ultra의 실제 의미를 환경에서 확인한다. 최대 추론과 자동 위임을 결합한 설정이면 두 효과의 필요성을 함께 평가하고 단순 병렬화 토글로 설명하지 않는다. 병렬화 권고는 에이전트 실행 권한을 새로 부여하지 않는다.

플랫폼에서 확인된 실제 모델·버전과 지원되는 추론수준만 확정 추천한다. 이름이나 등급이 다른 환경에서는 작업 적합성을 현재 선택지에 맞춰 판단한다. 버전이 확인되지 않았으면 임의로 최신 버전을 붙이지 않는다.

Pre-Plan에서는 이미 제공된 선택지 정보를 사용하고, 확인할 수 없으면 역할 기준의 잠정 추천과 확인 한계를 밝힌다. API와 앱의 지원 범위가 다를 수 있으므로 공식 안내의 모델 목록을 실제 환경의 선택지로 간주하지 않는다.

## 단계 판별과 라우팅 맥락

사용자가 단계를 말하지 않아도 현재 수행하려는 행동을 기준으로 조용히 판별한다. 최초 호출의 라우팅 맥락은 유지하되, 단계 자체는 엄격한 state machine이 아니며 `Implement → 짧은 조사 → Plan 수정 → Implement` 같은 왕복을 자연스럽게 허용한다.

| 현재 의도 | 보통의 신호 | 이 스킬의 역할 |
|---|---|---|
| **Pre-Plan** | 대략적 요구만 있고, 아직 실제 코드/구조를 깊게 살피지 않음 | 깊은 조사 없이 계획용과 예상 구현용 구성을 짧게 권고 |
| **Plan** | 저장소, 코드, 데이터 흐름, 제약을 조사하며 방향과 순서를 결정함 | 실제 발견사항을 반영해 구현용 구성을 다시 권고 |
| **Implement** | 구체적 방향을 바탕으로 수정·테스트·디버깅·검증 중임 | 정상 진행을 우선하고, 구체적 과부족이나 품질 격차가 있을 때 안전 경계에서 변경 권고 |

묵시적 호출에서 여러 의도가 섞이면 사용자가 지금 요청한 주된 행동을 우선한다. 다만 **명시 호출은 언제나 위의 추천 전용 턴 규칙이 우선**하며, 작업 설명을 실제 Plan·Implement 진입 지시로 해석하지 않는다.

## 공통 권고 원칙

1. 필요한 결과 품질을 먼저 정한다. 작동 여부나 테스트 통과만으로 설계·표현·시각 품질까지 충족했다고 보지 않는다. 명시된 예산·기한은 제약으로 지키고, 그 안에서 품질과 검토·재작업 부담을 함께 고려한다.
2. 파일 수, 에이전트 수, 테스트 실패 수, 토큰 수는 참고 신호일 뿐 절대 임계값이 아니다.
3. 어려움은 단순 규모와 다르다. 작은 변경도 보안·결제·데이터 손실·비가역 변경에 닿으면 높은 판단 능력과 검증 예산이 필요할 수 있다.
4. 기존 패턴의 국소 변경이나 명확한 재현·검증이 가능한 버그는 가벼운 후보도 적극 비교한다. CRUD라는 이름만으로 권한·동시성·데이터 무결성 판단까지 단순하다고 가정하지 않는다.
5. 새 아키텍처, 상충하는 요구, 불명확한 장애 원인, 여러 시스템의 상호작용은 더 강한 문제 해결 능력이 필요한 신호다. 높은 완성도의 결과물도 강한 모델의 정당한 용도이며 비가역 위험이 있어야만 추천할 수 있는 것은 아니다.
6. 여러 가설·제약을 함께 다루거나 반복 검증을 설계해야 하면 더 높은 추론수준을 비교한다. 모델과 추론수준 모두 필요하면 함께 바꿀 수 있고, 한 축만 필요하면 그 축만 바꾼다.
7. 독립적인 조사·검증·구현 흐름이 있고 결과의 통합 책임과 경계가 명확할 때 병렬화를 고려한다. 동일 파일을 동시에 고치거나 결과가 순차적으로 의존하면 보통 단일 흐름이 더 안전하다.

## 과소·과잉 추천을 함께 막는 기준

Pre-Plan의 정보 부족, “복잡해 보임”이라는 인상, 처음 보는 기술이라는 사실만으로 최상위 모델이나 높은 추론수준을 권하지 않는다. 반대로 정보가 부족하다는 이유만으로 낮은 구성을 고르거나, 계획 중이라는 이유로 이미 드러난 설계 난이도를 무시하지 않는다. 알려진 요구에 근거해 잠정 추천하고 추천을 바꿀 핵심 조건을 밝힌다.

추론수준은 아래의 작업 신호와 선택 모델의 지원 범위를 함께 보고 고른다. 표는 출발점이며 모델별 효과를 보장하는 성능표가 아니다.

| 작업 신호 | 비교할 추론수준 |
|---|---|
| 요구와 정답이 명확하고 판단·검증이 국소적임 | Low 등 지원되는 낮은 수준 |
| 범위가 정해진 문제 해결에 몇 가지 선택과 영향 확인이 필요함 | Medium 등 중간 수준 |
| 경쟁하는 가설·제약, 어려운 설계 판단, 깊은 검증이나 높은 완성도가 필요함 | High 등 높은 수준 |
| 깊은 추론이 핵심이고 높은 수준을 넘어서는 추가 사고의 이점을 구체적으로 설명할 수 있음 | 지원되는 xhigh·max·Ultra 등, 실측이 없으면 잠정 권고와 지연·비용 부담을 명시 |

상향·하향·유지 모두 같은 비교 기준을 적용한다. 더 가벼운 후보의 품질·검증 부담과 더 강한 후보의 추가 이점을 함께 검토한다. “상향의 필요성을 증명하지 못하면 무조건 하향”하거나 “고품질이면 무조건 최상위”로 결론 내리지 않는다. 비교 근거가 부족하면 잠정 판단과 확인할 항목을 밝힌다.

## 모든 추천에 상위·하위 미선택 이유 포함

Pre-Plan의 계획용·예상 구현용 추천, Plan의 재추천, Implement의 상향·하향 handoff와 현재 구성 유지 답변에 모두 적용한다. 정상 진행 중에는 비교를 반복 출력하지 않는다.

- **선택 이유**: 작업의 판단 난도·품질 요구와 확인된 검증 수단에 연결한다.
- **더 높은 모델 미선택**: 실제 선택지에서 의미 있는 상위 후보를 이름으로 밝히고, 추가 능력이 줄일 오류·재작업이나 품질 이점이 현재 요구에서 크지 않은 이유를 설명한다. 단순히 비싸거나 과하다는 말로 끝내지 않는다.
- **더 낮은 모델 미선택**: 의미 있는 하위 후보를 이름으로 밝히고, 충족하기 어려울 수 있는 판단·품질 요구나 재작업 부담을 설명한다. 확인된 한계와 예상 위험을 구분한다.
- 가능한 한 같은 추론수준에서 모델을 비교하고, 추론수준을 더 높이거나 낮추지 않은 이유도 별도로 설명한다. 두 축이 모두 다르면 어느 차이가 판단 근거인지 밝힌다.
- 끝단이면 `상위 후보 없음`·`하위 후보 없음`과 확인한 선택 범위를 적는다. 선택지나 작업별 우열이 불명확하면 `비교 불가: <확인 한계>`라고 쓰며 가상의 서열을 만들지 않는다.
- 가벼운 후보도 요구 품질을 동등하게 충족하고 강한 후보의 추가 이점이 작으면 가벼운 후보를 추천한다. 상위 후보의 품질 이점이 실질적이면 반영한다. 양쪽을 배제할 근거가 부족하면 잠정 판단과 재평가 조건을 밝히며 부족함을 꾸며내지 않는다.

계획용과 구현용 추천·비교 근거가 같으면 묶어 설명할 수 있다. 아래 형식의 비교 항목은 간결하게 쓰되 생략하지 않는다.

## Pre-Plan: 작업 근거에 따른 잠정 추천

아직 코드, 문서, 외부 시스템을 깊게 조사하지 않는다. 요구 설명에서 이미 알 수 있는 난이도·품질·위험·불확실성을 사용한다. 모델 후보를 확인하는 일과 작업 저장소의 깊은 조사는 구분한다. 계획 자체에 필요한 판단과 예상 구현에 필요한 판단을 각각 평가하고, 남은 불확실성은 한 줄로 명시한다.

다음 형식으로 답한다. 명시 호출에서는 이보다 깊은 계획이나 조사를 시작하지 않는다.

```text
작업 유형: <짧은 분류>
판단: <Pre-Plan>

계획 추천: <모델> / <추론수준>
예상 구현 추천: <모델> / <추론수준>
더 높은 모델 미선택: <상위 후보명과 이유 또는 상위 후보 없음/비교 불가>
더 낮은 모델 미선택: <하위 후보명과 이유 또는 하위 후보 없음/비교 불가>
추론수준 비교: <선택 이유 / 더 높이지 않은 이유 / 더 낮추지 않은 이유, 끝단이면 후보 없음>
Ultra/병렬화: <권고 여부와 짧은 이유>

근거:
- <작업 난이도·필요한 결과 품질에 따른 모델 선택 이유>
- <판단·탐색·검증 부담에 따른 추론수준 선택 이유>
- <관련 대안과의 차이, 남은 불확실성 또는 추천을 바꿀 조건>

다음 단계: (plan) 지시를 기다림 — 계획을 작성한 뒤 구현 구성을 재추천하고, 이후 (implement) 중 구성의 과부족을 감시함
```

## Plan: 발견에 근거한 재추천

사용자가 계획을 시작하라고 지시한 후속 턴에서는 필요한 만큼 실제 코드·구조·의존성·검증 수단을 조사하여 **실제 계획을 작성한다**. 계획에 구현 경로, 주요 결정, 위험과 검증 방법을 담는다. 계획을 완벽하게 만들기 위해 끝없이 탐색하지 않는다.

계획을 제시한 뒤 같은 응답의 끝에서 발견한 사실로 구현용 구성을 새로 평가한다. 이전 추천이나 계획에 사용한 모델을 가린 상태에서 비교하고, 달라졌다면 작업 근거를 밝힌다. 같아도 필요한 품질과 검증 부담에 왜 맞는지 설명한다. 이 추천만으로 구현을 시작하지 않는다.

```text
구현 추천: <모델> / <추론수준>
더 높은 모델 미선택: <상위 후보명과 이유 또는 상위 후보 없음/비교 불가>
더 낮은 모델 미선택: <하위 후보명과 이유 또는 하위 후보 없음/비교 불가>
추론수준 비교: <선택 이유 / 더 높이지 않은 이유 / 더 낮추지 않은 이유, 끝단이면 후보 없음>
Ultra/병렬화: <권고 여부>

계획 발견사항:
- <실제 구조 또는 제약>
- <영향 범위와 검증 방법>

권고 이유:
- <필요한 결과 품질과 관련 대안에 비춘 모델 선택 이유>
- <판단·탐색·검증 부담에 비춘 추론수준 선택 이유>
- <병렬화가 유효하거나 부적절한 이유>
```

## Implement: 진행하며 구성의 과부족 감시

구현 중에는 권고를 반복 출력하지 않는다. 현재 설정으로 신뢰성 있게 진행할 수 있다면 코드 수정, 테스트, 조사, 작은 계획 수정까지 계속 수행한다. 이는 실행을 계속할 판단이며 현재 설정이 최적이라는 추천 근거는 아니다. 한 번의 실패, 낯선 라이브러리, 느린 테스트, 다른 설정도 가능하다는 이유만으로 중단하지 않는다.

다음 중 하나가 **구체적 증거와 함께 실질적으로(materially) 발생**했을 때만 구성 변경을 고려한다.

- 핵심 설계 결정을 좌우하는 구조나 도메인 제약이 집중 조사 후에도 불명확하다.
- 문제의 원인이 여러 계층·시스템에 걸쳐 있으며, 현재 탐색·검증 예산으로 신뢰할 만한 가설과 검증을 유지하기 어렵다.
- 보안, 개인정보, 금전, 데이터 무결성, 비가역 운영 변경처럼 오류 비용이 큰 영역에서 현재 검증 수준이 충분하지 않다.
- 기능 검증을 통과해도 요구한 설계·표현·시각 품질이 충족되지 않고, 집중 보완 뒤에도 핵심 품질 격차가 남는다.
- 독립 workstream이 명확히 드러났고, 병렬 조사 또는 검증이 전체 위험·시간을 실질적으로 줄이지만 현 구성으로는 이를 적절히 조율할 수 없다.
- 누적된 작업 범위나 새 증거가 처음 가정과 크게 달라져, 이미 선택한 모델의 문제 해결 능력 또는 현재 추론수준의 사고 깊이가 현실적으로 부족해졌다.
- 실제 작업이 예상보다 명확하고 좁아져, 더 낮은 모델·추론수준으로도 남은 구현과 검증을 신뢰성 있게 마칠 수 있다. 단순히 더 싼 선택지가 있다는 이유만으로는 중단하지 않는다.

중단은 실행 중인 원자적 작업, 데이터 변경, 마이그레이션, 배포, 테스트의 중간이 아니라 **안전 경계(safe boundary)** 에서 한다. 가능한 안전 경계는 현재 파일의 일관된 저장 후, 하나의 테스트/조사 단위 완료 후, 다음 비가역 조치 직전이다. 사용자 승인이나 별도 권한이 필요한 행동은 상향 추천이 있어도 수행하지 않는다.

상향 또는 하향이 필요하면 즉시 멈추기 전에 현재 단위를 안전하게 마무리하고, 다음 handoff를 제공한다. 이미 적용한 변경, 실행한 검증, 미해결 위험을 숨기지 않는다.

```text
[구성 변경 권고 — 안전 경계 도달]
현재 단계: Implement
현재 구성: <모델> / <추론수준>

완료한 작업:
- <완료·검증된 단위>

발견한 사실:
- <구체적 증거 또는 재현 결과>

왜 현재 구성이 과하거나 부족한가:
- <남은 작업의 난이도, 결과 품질, 판단의 깊이와 의존 관계, 위험, 불확실성 또는 병렬성의 실제 변화>

권장 재개 구성: <모델> / <추론수준>
권장 구성 선택 이유: <남은 작업에 필요한 판단·품질과 검증>
더 높은 모델 미선택: <상위 후보명과 이유 또는 상위 후보 없음/비교 불가>
더 낮은 모델 미선택: <하위 후보명과 이유 또는 하위 후보 없음/비교 불가>
추론수준 비교: <선택 이유 / 더 높이지 않은 이유 / 더 낮추지 않은 이유, 끝단이면 후보 없음>
Ultra/병렬화: <필요 여부와 분할 가능한 workstream>

재개 시 첫 단계:
1. <확인 또는 결정할 핵심 항목>
2. <그 뒤의 안전한 다음 행동>
```

구성 변경 추천 뒤에는 다음 사용자 메시지의 명시적 Plan·Implement 지시가 있을 때만 재개한다. 사용자는 권장 구성을 적용하거나 현재 설정으로 진행하도록 선택할 수 있다. 변경 없이도 안전하게 진행 가능한 대안이 있으면 먼저 짧게 제시할 수 있다.

## 재평가를 줄이는 규칙

동일한 사실을 매 단계 되풀이해 추천을 갱신하지 않는다. 다음 중 의미 있는 변화가 있을 때만 재평가한다.

- 난이도 또는 핵심 설계의 성격
- 필요한 탐색 범위·검증 판단의 난도
- 병렬화할 수 있는 독립성
- 실패 비용과 위험도
- 요구한 결과 품질 또는 실제 산출물의 품질 격차
- 결정에 영향을 주는 불확실성

사용자가 명시적으로 다른 모델·추론수준을 묻거나, Plan이 실제 조사 결과로 끝나거나, Implement에서 실질적인 구성 과부족이 드러난 경우도 재평가 시점이다. 그 밖에는 현재 작업을 계속한다.

스킬 자체를 검증할 때는 [추천 편향 회귀 검토](references/routing-checks.md)를 사용한다. 일반적인 모델 추천마다 이 검토 전체를 실행할 필요는 없다.
