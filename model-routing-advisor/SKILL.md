# 모델 라우팅 어드바이저

사용자의 작업을 대신 설계하거나 불필요하게 멈추게 하지 않으면서, **현재 작업에 충분한 가장 낮은 구성(Minimum Sufficient Configuration, MSC)** 을 제안한다. 권고는 강제가 아니다. 사용자가 이미 선택한 모델 또는 추론수준을 존중하며, 위험·난이도·작업 범위가 실제로 달라질 때만 재평가한다.

이 스킬의 문구·추천 기준 자체를 검토하거나 수정해 달라는 요청은 라우터 실행 요청이 아니다. 그 경우 요청받은 스킬 점검·수정을 수행한다.

## 명시 호출은 추천 전용 턴

사용자가 `$model-routing-advisor`, “model router 실행”, “모델 추천 먼저” 등으로 이 스킬을 **명시 호출**하면, 이 규칙이 아래의 일반적인 Plan·Implement 진행 규칙보다 우선한다.

응답을 시작하기 전에 **사용자 메시지와 이전 대화만으로** 라우터 단계를 정한다. 새 작업의 요구만 설명하고 실제 조사·계획·수정 결과가 아직 없다면 Pre-Plan이다. “추가해야 해”, “확장 가능한 구조를 고려해야 해” 같은 표현은 추천할 작업의 설명이지, 같은 턴에서 계획·구현을 시작하라는 승인이 아니다. Codex 앱의 Plan Mode 같은 UI 실행 모드도 라우터의 Plan 단계로 간주하지 않는다. 라우터의 Plan은 사용자가 후속 메시지로 계획을 시작하라고 지시했거나, 이전 대화에서 이미 그 작업의 실제 조사·계획이 진행된 경우다.

- 해당 응답에서는 현재 요청 단계의 모델·추론수준·Ultra/병렬화 권고, 선택 근거와 상위·하위 모델 미선택 이유만 제공하고 응답을 끝낸다. 같은 메시지에 계획 수립이나 구현 요청이 함께 있어도 실행하지 않는다.
- Pre-Plan 명시 호출에서는 저장소·코드를 깊게 조사하지 않는다. Plan 명시 호출에서는 추천 근거에 필요한 읽기 전용 조사만 하고, 실제 계획 문서는 만들지 않는다. Implement 중 명시 호출은 현재 안전 경계에서 평가한 뒤 추가 수정·테스트를 진행하지 않는다.
- 권장 설정이 현재 구성과 같거나 상향 권고가 없더라도 추천 전용 턴 원칙은 같다. “현재 설정으로 충분”하다고 답한 뒤 같은 응답에서 본 작업을 시작하지 않는다.
- 응답 마지막에는 재개할 다음 행동을 한 줄로 알린다. 사용자가 다음 메시지에서 `(plan)`, `(implement)` 또는 동등한 진행 지시를 보내면 현재 설정으로 재개한다. 모델 변경은 재개의 필수 조건이 아니다.

예: `$model-routing-advisor 구독 기능과 플랜별 사용량 제한을 추가해야 해. 확장 가능한 구조도 고려해 줘.` → **Pre-Plan**으로 계획용·예상 구현용 모델/추론수준과 근거를 권고하고 응답 종료. 저장소 탐색, 한도 정책 결정, 설계 질문, 계획 작성은 후속 사용자 지시 전까지 하지 않는다.

이 규칙은 사용자가 직접 router를 요청한 경우에만 적용한다. router가 묵시적으로 선택됐고 현재 설정이 충분하면 아래 일반 흐름대로 본 작업을 계속할 수 있다.

## 첫 호출 이후 같은 목표에서 계속 적용

첫 호출의 추천 전용 턴이 끝나도 **같은 대화의 같은 목표**에는 라우팅 판단을 이어간다. 사용자가 매 단계마다 스킬을 다시 호출할 필요는 없다. 후속 메시지에 스킬 이름이 없어도 이전 라우팅 결과와 현재 작업 단계를 확인하고 아래 전환을 따른다.

- 후속 `(plan)` 또는 동등한 계획 지시: 추천 전용 턴을 반복하지 말고 실제 계획을 작성한다. 계획을 마친 같은 응답 끝에서 발견사항에 근거해 **구현 모델·추론수준을 다시 추천**한다. 초기 예상과 같아도 유지 이유를 짧게 밝힌다. 그 뒤에는 사용자의 구현 지시를 기다린다.
- 후속 `(implement)` 또는 동등한 구현 지시: 별도 스킬 호출이나 모델 변경을 요구하지 않고 구현을 시작한다. 진행 중 현재 구성의 과부족을 감시하고, 실질적 불일치가 확인되면 안전 경계에서 중단해 새 구성을 추천한다.
- 후속 메시지에 `$model-routing-advisor`를 **다시 명시**했다면 그 턴은 다시 추천 전용으로 처리한다. 반대로 단계 진행 지시만 있다면 첫 호출의 추천 전용 규칙을 재적용하지 않는다.

사용자 메시지 없이 Pre-Plan → Plan → Implement를 자동으로 넘기지 않는다. 이 맥락은 같은 대화 안에서만 유지한다. 새 대화나 독립된 목표에는 이전 목표의 라우팅을 강제로 적용하지 않는다.

## 자동 호출과 재개 게이트

명시 호출뿐 아니라, 현재 설정과 요구의 격차가 실질적으로 클 때 자동으로 이 스킬을 사용한다. 자동 호출 신호는 고난도 설계 선택, 넓은 탐색 또는 검증, 고위험·비가역 변경, 긴 의존 관계를 가진 작업이며, 이 중 하나만으로 자동 호출을 강제하지 않는다. 현재 구성으로 안전하고 신뢰성 있게 진행할 수 있다면 호출하거나 중단하지 않는다.

묵시적 호출에서 Pre-Plan 또는 Plan의 새 상향 권고를 제시하면 **권고와 handoff만** 포함하고 끝낸다. 그 응답 안에서 계획을 작성하거나 Implement로 전환하지 않는다. 추천 자체는 다음 단계 진행 승인이 아니다.

권고를 낸 뒤에는 같은 목표에 대해 대기 상태를 대화 맥락에 유지한다. 후속 사용자 메시지 없이 Plan·Implement를 자동으로 재개하지 않는다. 사용자가 `(plan)`, `(implement)` 또는 동등하게 다음 행동을 명시하면 이를 현재 설정으로 진행하라는 승인으로 간주해 위의 후속 단계에서 재개한다. 모델·추론수준 변경은 필수가 아니며, 사용자가 변경 사실을 알리면 새 설정을 반영한다.

동일 목표의 후속 단계는 최초 라우팅 판단을 이어서 적용한다. 핵심 설계, 필요한 탐색 범위·검증 난도, 실패 비용, 또는 독립 병렬성에 실질적 변화가 있을 때만 다시 권고한다. 새롭고 독립된 목표는 별도로 판별한다.

## 판단 축

세 축은 서로 영향을 줄 수 있지만, 단일 규칙이나 점수표로 고정하지 않는다.

- **모델(Model)**: 문제 해결 능력과 작업 적합성이다. 상충하는 제약, 모호한 원인 분석, 어려운 설계 선택, 정밀한 종합 판단이 필요할수록 더 강한 모델을 고려한다. 이름·세대·가격만으로 작업별 우열을 단정하지 않는다.
- **추론수준(Reasoning)**: 답을 결정할 때 투입하는 사고의 깊이와 양이다. 어려운 가설 비교, 다단계 의존성, 정밀한 검증 판단이 필요할수록 높인다. 긴 작업은 참고 신호지만, 파일이 많거나 테스트가 오래 걸린다는 이유만으로 올리지 않는다. 컨텍스트 창, 도구 호출 한도, 작업 시간이나 테스트 실행량을 늘려 주는 설정으로 설명하지 않는다.
- **Ultra와 병렬화**: 환경의 실제 설명을 확인한다. Ultra가 최대 추론과 자동 위임을 결합한 설정이면 두 효과를 함께 평가하고, 단순 병렬화 토글로 설명하지 않는다. 병렬화는 독립된 작업 흐름과 결과 통합·검증의 이점이 있을 때 별도로 고려한다. 추천 자체를 하위 에이전트 실행 승인으로 간주하지 않는다.

현재 환경이 제공하는 모델 목록·설명과 지원 추론수준을 우선 확인하고, 실제 선택 가능한 조합만 추천한다. Pre-Plan에서는 이미 제공된 정보만 사용하며, 선택지를 확인할 수 없으면 역할 기준의 잠정 추천과 확인 한계를 밝힌다. 확인을 위해 저장소를 깊게 조사하거나 과거 기본 모델을 현재 선택지처럼 단정하지 않는다.

모델별 역할과 사고 예산의 일반 원칙은 [OpenAI 모델 선택 안내](https://developers.openai.com/api/docs/guides/model-selection)와 [추론수준 안내](https://developers.openai.com/api/docs/guides/reasoning)를 참고한다. API와 앱의 지원 범위가 다를 수 있으므로 실제 환경의 선택지를 함께 확인한다.

## 단계 판별과 라우팅 맥락

사용자가 단계를 말하지 않아도 현재 수행하려는 행동을 기준으로 조용히 판별한다. 최초 호출의 라우팅 맥락은 유지하되, 단계 자체는 엄격한 state machine이 아니며 `Implement → 짧은 조사 → Plan 수정 → Implement` 같은 왕복을 자연스럽게 허용한다.

| 현재 의도 | 보통의 신호 | 이 스킬의 역할 |
|---|---|---|
| **Pre-Plan** | 대략적 요구만 있고, 아직 실제 코드/구조를 깊게 살피지 않음 | 깊은 조사 없이 계획용과 예상 구현용 구성을 짧게 권고 |
| **Plan** | 저장소, 코드, 데이터 흐름, 제약을 조사하며 방향과 순서를 결정함 | 실제 발견사항을 반영해 구현용 구성을 다시 권고 |
| **Implement** | 구체적 방향을 바탕으로 수정·테스트·디버깅·검증 중임 | 정상 진행을 우선하고, 현재 구성의 실질적인 과부족이 확인될 때만 안전 경계에서 변경 권고 |

묵시적 호출에서 여러 의도가 섞이면 사용자가 지금 요청한 주된 행동을 우선한다. 다만 **명시 호출은 언제나 위의 추천 전용 턴 규칙이 우선**하며, 작업 설명을 실제 Plan·Implement 진입 지시로 해석하지 않는다.

## 공통 권고 원칙

1. 필요한 품질·정확성·검증 가능성을 먼저 정하고, 이를 만족하는 MSC를 고른다. 사용자가 밝힌 품질 우선순위, 대기 시간, 반복 실행 빈도와 사용량 제약을 함께 고려한다. 더 높은 설정의 이점이 구체적일 때만 올리고, 가격이나 속도의 정확한 수치는 확인 없이 만들지 않는다.
2. 파일 수, 에이전트 수, 테스트 실패 수, 토큰 수는 참고 신호일 뿐 절대 임계값이 아니다.
3. 어려움은 단순 규모와 다르다. 작은 변경도 보안·결제·데이터 손실·비가역 변경에 닿으면 높은 판단 능력과 검증 예산이 필요할 수 있다.
4. 평범한 CRUD, 기존 패턴의 국소 변경, 명확한 재현·수정·검증이 가능한 버그는 낮거나 중간 구성부터 시작한다.
5. 새 아키텍처 선택, 상충하는 요구, 근본 원인이 불명확한 장애, 여러 시스템의 비자명한 상호작용은 더 강한 모델을 고려한다.
6. 다단계 조사와 모듈 간 영향 추적에서 가설·제약을 함께 판단하기 어려울 때 더 높은 추론수준을 고려한다. 모델과 추론수준은 독립적으로 판단하며, 둘 다 바꿔야 하면 각 축의 근거를 따로 밝힌다.
7. 독립적인 조사·검증·구현 흐름이 둘 이상 있고 결과의 통합 책임과 경계가 명확할 때 병렬화를 고려한다. 동일 파일을 동시에 고치거나 결과가 순차적으로 의존하면 보통 단일 흐름이 더 안전하다. Ultra가 자동 위임을 포함하면 최대 추론과 위임 모두의 필요성을 확인한다.

## 과도한 상향을 막는 기준

Pre-Plan의 불확실성, "복잡해 보임"이라는 인상, 넓은 요구 설명, 또는 처음 보는 기술이라는 사실만으로 상위 모델이나 높은 추론수준을 권하지 않는다. 이 단계에서는 안전한 Plan 조사와 구현 중 재평가가 가능하므로, 모르는 사실은 상향 근거가 아니라 확인할 항목이다.

고정된 `Terra / Medium`을 기본값으로 삼지 않는다. 현재 선택지 중 경량 모델은 명확한 국소 수정·기존 패턴 적용·쉽게 검증할 수 있는 작업에, 범용 모델은 여러 모듈의 판단·설계 선택·연결된 변경에 우선 검토한다. 최상위 모델은 아래의 구체적 필요가 있을 때 검토한다. 이는 후보를 좁히는 기준이며 모델별 성능을 보장하는 서열표가 아니다.

최상위 모델을 비가역 위험이 있는 작업으로만 제한하지 않는다. 되돌릴 수 있는 작업도 여러 핵심 제약의 충돌, 어려운 원인 규명, 높은 정확성이 필요한 종합 판단 때문에 더 강한 모델이 유효할 수 있다. Pre-Plan에서는 요구에 이미 드러난 판단 난도와 필요한 품질을 근거로 삼고, Plan 이후에는 실제 발견사항과 검증 수단을 반영한다. 위험 영역이라는 이름만으로 자동 상향하거나, 검증·권한 문제를 모델 상향으로 해결하려 하지 않는다.

추론수준도 고정 기본값으로 두지 않는다. 명확한 실행·단순 수정은 낮은 수준, 판단이 필요한 구현·계획은 중간 수준, 어려운 가설 비교·깊은 디버깅은 높은 수준부터 검토한다. `xhigh`·`max`·`ultra` 등 상위 수준은 하위 수준보다 필요한 추가 사고가 무엇인지 설명하고, 가능하면 대표 작업의 결과로 이점을 확인한다. 수행하지 않은 비교 평가를 실측 근거처럼 제시하지 않는다.

## 모든 추천에 상위·하위 미선택 이유 포함

Pre-Plan의 계획용·예상 구현용 추천, Plan의 재추천, Implement의 상향·하향 handoff와 현재 구성 유지 답변에 모두 적용한다. 추천이 없고 정상 진행 중이면 비교를 반복 출력하지 않는다.

- **선택 이유**: 현재 작업의 판단 난도·품질 요구와 확인된 검증 수단에 연결해 설명한다.
- **더 높은 모델을 추천하지 않은 이유**: 실제 선택지에서 가장 가까운 의미 있는 상위 후보를 이름으로 밝히고, 추가 능력으로 줄일 오류나 재작업이 현재 범위에서 크지 않은 이유를 설명한다. 단순히 "과함"이나 "비쌈"으로 끝내지 않는다.
- **더 낮은 모델을 추천하지 않은 이유**: 가장 가까운 의미 있는 하위 후보를 이름으로 밝히고, 충족하기 어려울 수 있는 구체적 판단·품질 요구나 재작업 위험을 설명한다. 확인된 한계와 예상 위험을 구분하고, 실패하지 않은 모델을 실패했다고 단정하지 않는다.
- 모델 비교는 가능한 한 같은 추론수준에서 하고, 추론수준을 고른 이유는 별도로 설명한다. 더 높은 추론수준이 불필요한 이유와 더 낮은 추론수준으로 부족할 수 있는 이유도 짧게 포함한다. 두 축이 모두 달라지는 후보를 비교하면 어느 차이를 근거로 삼았는지 밝힌다.
- 최상위·최하위 선택이면 각각 `상위 후보 없음`·`하위 후보 없음`과 확인한 선택 범위를 적는다. 선택지나 작업별 우열을 확인할 수 없으면 `비교 불가: <확인 한계>`라고 쓰고 가상의 후보나 서열을 만들지 않는다.
- 하위 후보로도 충분하다면 하위를 추천한다. 더 높은 후보의 이점이 요구 품질을 충족하는 데 필요하다면 상위를 추천한다. 양쪽을 배제할 근거가 부족하면 잠정 판단임을 밝히고 다음 재평가 조건을 제시한다. 부족함을 꾸며내어 현재 추천을 정당화하지 않는다.

계획용과 구현용 추천 및 비교 근거가 같으면 한 번에 묶어도 된다. 추천이 다르면 각각 설명한다. 아래 형식의 비교 항목은 간결하게 쓰되 생략하지 않는다.

## Pre-Plan: 짧고 보수적인 예상

아직 코드, 문서, 외부 시스템을 깊게 조사하지 않는다. 요구 설명에서 이미 알 수 있는 범위·위험·불확실성만 사용한다. 부족한 맥락을 이유로 과도한 모델을 권하지 말고, 불확실성은 한 줄로 명시한다.

다음 형식으로 답한다. 명시 호출에서는 이보다 깊은 계획이나 조사를 시작하지 않는다.

```text
작업 유형: <짧은 분류>
판단: <Pre-Plan>

계획 추천: <모델> / <추론수준>
예상 구현 추천: <모델> / <추론수준>
Ultra/병렬화: <권고 여부와 짧은 이유>

모델 비교: <계획용·예상 구현용 공통 또는 각각>
- 선택 이유: <필요한 판단과 품질>
- 더 높은 모델 미선택: <상위 후보명과 이유 또는 상위 후보 없음/비교 불가>
- 더 낮은 모델 미선택: <하위 후보명과 이유 또는 하위 후보 없음/비교 불가>
추론수준 비교: <선택 이유 / 더 높이지 않은 이유 / 더 낮추지 않은 이유, 끝단이면 후보 없음>

근거:
- <난이도·깊이 신호>
- <의존 관계·검증 난도 신호>
- <현재 정보로 남은 불확실성>

다음 단계: (plan) 지시를 기다림 — 계획을 작성한 뒤 구현 구성을 재추천하고, 이후 (implement) 중 구성의 과부족을 감시함
```

예시:

```text
작업 유형: 기존 RAG를 tool-calling 기반 agent 구조로 전환
판단: Pre-Plan

계획 추천: GPT-6.1 Sol / Medium
예상 구현 추천: GPT-6.1 Sol / Medium
Ultra/병렬화: 보류 — 코드 구조와 독립 가능한 workstream을 아직 확인하지 않음

모델 비교: 계획용·예상 구현용 공통, Astra·GPT-6.1 Sol·GPT-6 Luna가 선택 가능한 환경의 예시
- 선택 이유: 기존 RAG와 도구 실행 흐름의 호환성을 판단하고 설계 대안을 비교해야 함
- 더 높은 모델 미선택: GPT-6 Astra / Medium의 추가 분석 능력이 필요한 상충 제약은 아직 확인되지 않음
- 더 낮은 모델 미선택: GPT-6 Luna / Medium보다 범용 모델을 우선 검토함. 기존 패턴 적용을 넘어 호출·상태 흐름을 결정해야 하므로, 경량 모델에서는 설계 재검토가 늘 수 있다는 잠정 판단임
추론수준 비교: Medium은 흐름 비교에 필요함 / High가 필요한 깊은 원인 분석은 아직 없음 / Low로 낮추면 여러 설계 대안의 비교가 얕아질 수 있음

근거:
- 아키텍처 선택과 기존 흐름의 호환성 판단은 필요하지만, 아직 고위험·비가역 제약은 확인되지 않음
- 여러 모듈의 변경과 검증이 예상되나, 독립성·영향 범위는 Plan 조사로 확인할 수 있음
- 변경이 기존 adapter의 국소 수정으로 한정되면 Plan 후 경량 모델로 낮출 수 있음
```

## Plan: 발견에 근거한 재추천

사용자가 계획을 시작하라고 지시한 후속 턴에서는 필요한 만큼 실제 코드·구조·의존성·검증 수단을 조사하여 **실제 계획을 작성한다**. 계획에 구현 경로, 주요 결정, 위험과 검증 방법을 담는다. 계획을 완벽하게 만들기 위해 끝없이 탐색하지 않는다.

계획을 제시한 뒤 같은 응답의 끝에서 구현용 구성을 다시 평가해 추천한다. 처음 예상과 달라진 이유를 명확히 하고, 낮출 수 있으면 낮춘다. 처음 예상과 같으면 왜 그대로 충분한지 설명한다. 이 추천만으로 구현을 시작하지 않는다.

```text
구현 추천: <모델> / <추론수준>
Ultra/병렬화: <권고 여부>

계획 발견사항:
- <실제 구조 또는 제약>
- <영향 범위와 검증 방법>

권고 이유:
- <모델 선택 이유>
- <추론수준 선택 이유>
- <병렬화가 유효하거나 부적절한 이유>

더 높은 모델 미선택: <상위 후보명과 이유 또는 상위 후보 없음/비교 불가>
더 낮은 모델 미선택: <하위 후보명과 이유 또는 하위 후보 없음/비교 불가>
추론수준 비교: <더 높이지 않은 이유 / 더 낮추지 않은 이유, 끝단이면 후보 없음>
```

예시:

```text
구현 추천: GPT-6 Luna / Medium
Ultra/병렬화: 권고하지 않음

계획 발견사항:
- 전환 대상은 adapter 두 개와 기존 통합 테스트로 제한됨
- 공개 인터페이스와 데이터 스키마는 바뀌지 않음

권고 이유:
- 설계 선택은 끝났고 기존 패턴을 따르는 구현임
- 영향 추적과 테스트 검증은 필요하지만 탐색 범위는 좁음
- 수정 순서가 서로 의존하고 같은 테스트 기반을 공유함

더 높은 모델 미선택: GPT-6.1 Sol / Medium의 설계 판단 이점은 작음. 구현 경로가 확정됐고 기존 통합 테스트로 변경 결과를 확인할 수 있음
더 낮은 모델 미선택: 하위 후보 없음. 이 예시에서 확인한 Astra·GPT-6.1 Sol·GPT-6 Luna 중 경량 후보를 선택함
추론수준 비교: High가 필요한 불명확한 가설은 없음 / Low보다 Medium을 유지해 adapter 간 호출·오류 처리와 테스트 결과를 함께 검토함
```

## Implement: 진행하며 구성의 과부족 감시

구현 중에는 권고를 반복 출력하지 않는다. 현재 설정이 작업에 적합하다면 코드 수정, 테스트, 조사, 작은 계획 수정까지 계속 수행한다. 한 번의 실패, 낯선 라이브러리, 느린 테스트, 미관상 더 좋은 설정이 있다는 이유만으로 중단하지 않는다.

다음 중 하나가 **구체적 증거와 함께 실질적으로(materially) 발생**했을 때만 구성 변경을 고려한다.

- 핵심 설계 결정을 좌우하는 구조나 도메인 제약이 집중 조사 후에도 불명확하다.
- 문제의 원인이 여러 계층·시스템에 걸쳐 있으며, 현재 탐색·검증 예산으로 신뢰할 만한 가설과 검증을 유지하기 어렵다.
- 보안, 개인정보, 금전, 데이터 무결성, 비가역 운영 변경처럼 오류 비용이 큰 영역에서 현재 검증 수준이 충분하지 않다.
- 독립 workstream이 명확히 드러났고, 병렬 조사 또는 검증이 전체 위험·시간을 실질적으로 줄이지만 현 구성으로는 이를 적절히 조율할 수 없다.
- 누적된 작업 범위나 새 증거가 처음 가정과 크게 달라져, 이미 선택한 모델의 문제 해결 능력 또는 현재 추론수준의 사고 깊이가 현실적으로 부족해졌다.
- 실제 작업이 예상보다 명확하고 좁아져, 더 낮은 모델·추론수준으로도 남은 구현과 검증을 신뢰성 있게 마칠 수 있다. 단순히 더 싼 선택지가 있다는 이유만으로는 중단하지 않는다.

중단은 실행 중인 원자적 작업, 데이터 변경, 마이그레이션, 배포, 테스트의 중간이 아니라 **안전 경계(safe boundary)** 에서 한다. 가능한 안전 경계는 현재 파일의 일관된 저장 후, 하나의 테스트/조사 단위 완료 후, 다음 비가역 조치 직전이다. 사용자 승인이나 별도 권한이 필요한 행동은 상향 추천이 있어도 수행하지 않는다.

상향 또는 하향이 필요하면 즉시 멈추기 전에 현재 단위를 안전하게 마무리하고, 다음 handoff를 제공한다. 이미 적용한 변경, 실행한 검증, 미해결 위험을 숨기지 않는다.

```text
[구성 변경 권고 — 안전 경계 도달]
현재 단계: Implement
현재 구성: <모델> / <추론수준>

완료한 작업:
- <완료·검증된 단위>

발견한 사실:
- <구체적 증거 또는 재현 결과>

왜 현재 구성이 과하거나 부족한가:
- <남은 작업의 난이도, 의존 관계, 위험, 불확실성 또는 병렬성의 실제 변화>

권장 재개 구성: <모델> / <추론수준>
Ultra/병렬화: <필요 여부와 분할 가능한 workstream>

권장 구성 선택 이유: <남은 작업에 필요한 판단과 검증>
더 높은 모델 미선택: <상위 후보명과 이유 또는 상위 후보 없음/비교 불가>
더 낮은 모델 미선택: <하위 후보명과 이유 또는 하위 후보 없음/비교 불가>
추론수준 비교: <선택 이유 / 더 높이지 않은 이유 / 더 낮추지 않은 이유, 끝단이면 후보 없음>

재개 시 첫 단계:
1. <확인 또는 결정할 핵심 항목>
2. <그 뒤의 안전한 다음 행동>
```

구성 변경 추천 뒤에는 다음 사용자 메시지의 명시적 Plan·Implement 지시가 있을 때만 재개한다. 사용자는 권장 구성을 적용하거나 현재 설정으로 진행하도록 선택할 수 있다. 변경 없이도 안전하게 진행 가능한 대안이 있으면 먼저 짧게 제시할 수 있다.

## 재평가를 줄이는 규칙

동일한 사실을 매 단계 되풀이해 추천을 갱신하지 않는다. 다음 중 의미 있는 변화가 있을 때만 재평가한다.

- 난이도 또는 핵심 설계의 성격
- 필요한 탐색 범위·검증 판단의 난도
- 병렬화할 수 있는 독립성
- 실패 비용과 위험도
- 결정에 영향을 주는 불확실성

사용자가 명시적으로 다른 모델·추론수준을 묻거나, Plan이 실제 조사 결과로 끝나거나, Implement에서 실질적인 구성 과부족이 드러난 경우도 재평가 시점이다. 그 밖에는 현재 작업을 계속한다.
