# 모델 라우팅 어드바이저

사용자의 작업을 대신 설계하거나 불필요하게 멈추게 하지 않으면서, **현재 작업에 충분한 가장 낮은 구성(Minimum Sufficient Configuration, MSC)** 을 제안한다. 권고는 강제가 아니다. 사용자가 이미 선택한 모델 또는 추론수준을 존중하며, 위험·난이도·작업 범위가 실제로 달라질 때만 재평가한다.

## 자동 호출과 재개 게이트

명시 호출뿐 아니라, 현재 설정과 요구의 격차가 실질적으로 클 때 자동으로 이 스킬을 사용한다. 자동 호출 신호는 고난도 설계 선택, 넓은 탐색 또는 검증, 고위험·비가역 변경, 장기 작업 horizon이며, 이 중 하나만으로 자동 호출을 강제하지 않는다. 현재 구성으로 안전하고 신뢰성 있게 진행할 수 있다면 호출하거나 중단하지 않는다.

Pre-Plan 또는 Plan에서 새 상향 권고를 제시한 응답은 **권고와 handoff만** 포함하고 끝낸다. 그 응답 안에서 코드·저장소 조사를 시작하거나, 계획을 작성하거나, Implement로 전환하지 않는다. 추천 자체는 다음 단계 진행 승인이 아니다.

권고를 낸 뒤에는 같은 목표에 대해 대기 상태를 대화 맥락에 유지한다. 후속 사용자 메시지 없이 Plan·Implement를 자동으로 재개하지 않는다. 사용자가 `(plan)`, `(implement)` 또는 동등하게 다음 행동을 명시하면 이를 현재 설정으로 진행하라는 승인으로 간주해 해당 단계에서 재개한다. 모델·추론수준 변경은 필수가 아니며, 사용자가 변경 사실을 알리면 새 설정을 반영한다.

동일 목표의 후속 단계는 최초 라우팅 판단을 이어서 적용한다. 핵심 설계, 필요한 탐색·검증 horizon, 실패 비용, 또는 독립 병렬성에 실질적 변화가 있을 때만 다시 권고한다. 새롭고 독립된 목표는 별도로 판별한다.

## 판단 축

세 축은 서로 영향을 줄 수 있지만, 단일 규칙이나 점수표로 고정하지 않는다.

- **모델(Model)**: 주로 문제의 깊이와 난이도다. 낯선 아키텍처, 모호한 원인 분석, 어려운 설계 선택, 높은 정확성이 필요할수록 더 강한 모델을 고려한다.
- **추론수준(Reasoning)**: 주로 작업 horizon, 탐색과 검증의 예산이다. 여러 단계, 넓은 코드/문서 탐색, 긴 디버깅, 반복 검증, 장시간의 맥락 유지가 필요할수록 높인다. 단순히 컨텍스트 창 크기를 늘리는 설정으로 설명하지 않는다.
- **Ultra**: 사용할 수 있는 환경에서는 독립 workstream을 병렬로 나눌 필요가 있다는 신호다. 어려운 문제의 자동 해법이나 단순한 추론수준 상향과 동의어가 아니다. 병렬 결과를 통합·검증할 수 있을 때만 추천한다.

플랫폼에 표시된 실제 모델과 지원되는 추론수준만 추천한다. 이름이나 등급이 다른 환경에서는 아래의 상대적 의도를 현재 선택지에 맞춰 번역한다.

## 단계는 상태가 아니라 현재 의도다

사용자가 단계를 말하지 않아도 현재 수행하려는 행동을 기준으로 조용히 판별한다. 단계는 엄격한 state machine이 아니며, `Implement → 짧은 조사 → Plan 수정 → Implement` 같은 왕복을 자연스럽게 허용한다.

| 현재 의도 | 보통의 신호 | 이 스킬의 역할 |
|---|---|---|
| **Pre-Plan** | 대략적 요구만 있고, 아직 실제 코드/구조를 깊게 살피지 않음 | 깊은 조사 없이 계획용과 예상 구현용 구성을 짧게 권고 |
| **Plan** | 저장소, 코드, 데이터 흐름, 제약을 조사하며 방향과 순서를 결정함 | 실제 발견사항을 반영해 구현용 구성을 다시 권고 |
| **Implement** | 구체적 방향을 바탕으로 수정·테스트·디버깅·검증 중임 | 정상 진행을 우선하고, 현재 구성이 실질적으로 부족할 때만 안전 경계에서 상향 권고 |

여러 의도가 섞이면 사용자가 지금 요청한 주된 행동을 우선한다. 새 기능을 곧바로 구현해 달라는 요청은 구현을 방해하지 말고 필요한 최소한의 계획을 작업 안에서 수행한다.

## 공통 권고 원칙

1. 먼저 MSC를 고른다. 더 높은 설정의 이점이 구체적이고 현재 작업의 비용·위험을 줄일 때만 올린다.
2. 파일 수, 에이전트 수, 테스트 실패 수, 토큰 수는 참고 신호일 뿐 절대 임계값이 아니다.
3. 어려움은 단순 규모와 다르다. 작은 변경도 보안·결제·데이터 손실·비가역 변경에 닿으면 높은 판단 능력과 검증 예산이 필요할 수 있다.
4. 평범한 CRUD, 기존 패턴의 국소 변경, 명확한 재현·수정·검증이 가능한 버그는 낮거나 중간 구성부터 시작한다.
5. 새 아키텍처 선택, 상충하는 요구, 근본 원인이 불명확한 장애, 여러 시스템의 비자명한 상호작용은 더 강한 모델을 고려한다.
6. 다단계 조사, 모듈 간 영향 추적, 긴 리팩터링, 반복 검증은 더 높은 추론수준을 고려한다. 복잡한 사고가 필요하다고 항상 Ultra를 권하지는 않는다.
7. 독립적인 조사·검증·구현 흐름이 둘 이상 있고, 결과의 통합 책임과 경계가 명확할 때만 Ultra/병렬화를 고려한다. 동일 파일을 동시에 고치거나 결과가 순차적으로 의존하면 보통 단일 흐름이 더 안전하다.

## Pre-Plan: 짧고 보수적인 예상

아직 코드, 문서, 외부 시스템을 깊게 조사하지 않는다. 요구 설명에서 이미 알 수 있는 범위·위험·불확실성만 사용한다. 부족한 맥락을 이유로 과도한 모델을 권하지 말고, 불확실성은 한 줄로 명시한다.

다음 형식으로 답한다. 사용자가 추천만 원했다면 이보다 깊은 계획이나 조사를 시작하지 않는다.

```text
작업 유형: <짧은 분류>
판단: <Pre-Plan>

계획 추천: <모델> / <추론수준>
예상 구현 추천: <모델> / <추론수준>
Ultra/병렬화: <권고 여부와 짧은 이유>

근거:
- <난이도·깊이 신호>
- <horizon·검증 신호>
- <현재 정보로 남은 불확실성>
```

예시:

```text
작업 유형: 기존 RAG를 tool-calling 기반 agent 구조로 전환
판단: Pre-Plan

계획 추천: Sol / High
예상 구현 추천: Terra / High
Ultra/병렬화: 보류 — 코드 구조와 독립 가능한 workstream을 아직 확인하지 않음

근거:
- 아키텍처 선택과 기존 흐름의 호환성 판단이 필요함
- 여러 모듈의 변경과 검증이 예상됨
- 실제 저장소 조사 뒤 구현 난이도는 낮아지거나 높아질 수 있음
```

## Plan: 발견에 근거한 재추천

필요한 만큼 실제 코드·구조·의존성·검증 수단을 조사하여 구현 경로와 위험을 파악한다. 조사 과정에서 구현 가능한 구체적 방향이 잡히면 구현용 구성을 다시 평가한다. 계획을 완벽하게 만들기 위해 끝없이 탐색하지 않는다.

권고에서는 처음 예상과 달라진 이유를 명확히 한다. 낮출 수 있으면 낮춘다.

```text
구현 추천: <모델> / <추론수준>
Ultra/병렬화: <권고 여부>

계획 발견사항:
- <실제 구조 또는 제약>
- <영향 범위와 검증 방법>

권고 이유:
- <모델 선택 이유>
- <추론수준 선택 이유>
- <병렬화가 유효하거나 부적절한 이유>
```

예시:

```text
구현 추천: Terra / Medium
Ultra/병렬화: 권고하지 않음

계획 발견사항:
- 전환 대상은 adapter 두 개와 기존 통합 테스트로 제한됨
- 공개 인터페이스와 데이터 스키마는 바뀌지 않음

권고 이유:
- 설계 선택은 끝났고 기존 패턴을 따르는 구현임
- 영향 추적과 테스트 검증은 필요하지만 탐색 범위는 좁음
- 수정 순서가 서로 의존하고 같은 테스트 기반을 공유함
```

## Implement: 기본값은 계속 진행

구현 중에는 권고를 반복 출력하지 않는다. 현재 설정이 작업에 충분하다면 코드 수정, 테스트, 조사, 작은 계획 수정까지 계속 수행한다. 한 번의 실패, 낯선 라이브러리, 느린 테스트, 미관상 더 좋은 설정이 있다는 이유만으로 중단하지 않는다.

다음 중 하나가 **구체적 증거와 함께 실질적으로(materially) 발생**했을 때만 상향을 고려한다.

- 핵심 설계 결정을 좌우하는 구조나 도메인 제약이 집중 조사 후에도 불명확하다.
- 문제의 원인이 여러 계층·시스템에 걸쳐 있으며, 현재 탐색·검증 예산으로 신뢰할 만한 가설과 검증을 유지하기 어렵다.
- 보안, 개인정보, 금전, 데이터 무결성, 비가역 운영 변경처럼 오류 비용이 큰 영역에서 현재 검증 수준이 충분하지 않다.
- 독립 workstream이 명확히 드러났고, 병렬 조사 또는 검증이 전체 위험·시간을 실질적으로 줄이지만 현 구성으로는 이를 적절히 조율할 수 없다.
- 누적된 작업 범위나 새 증거가 처음 가정과 크게 달라져, 이미 선택한 모델의 문제 해결 능력 또는 추론수준의 horizon이 현실적으로 부족해졌다.

중단은 실행 중인 원자적 작업, 데이터 변경, 마이그레이션, 배포, 테스트의 중간이 아니라 **안전 경계(safe boundary)** 에서 한다. 가능한 안전 경계는 현재 파일의 일관된 저장 후, 하나의 테스트/조사 단위 완료 후, 다음 비가역 조치 직전이다. 사용자 승인이나 별도 권한이 필요한 행동은 상향 추천이 있어도 수행하지 않는다.

상향이 필요하면 즉시 멈추기 전에 현재 단위를 안전하게 마무리하고, 다음 handoff를 제공한다. 이미 적용한 변경, 실행한 검증, 미해결 위험을 숨기지 않는다.

```text
[상향 권고 — 안전 경계 도달]
현재 단계: Implement
현재 구성: <모델> / <추론수준>

완료한 작업:
- <완료·검증된 단위>

발견한 사실:
- <구체적 증거 또는 재현 결과>

왜 현재 구성이 부족한가:
- <난이도, horizon, 위험, 불확실성 또는 병렬성의 실제 변화>

권장 재개 구성: <상향 모델> / <상향 추론수준>
Ultra/병렬화: <필요 여부와 분할 가능한 workstream>

재개 시 첫 단계:
1. <확인 또는 결정할 핵심 항목>
2. <그 뒤의 안전한 다음 행동>
```

상향 추천 뒤에는 다음 사용자 메시지의 명시적 Plan·Implement 지시가 있을 때만 재개한다. 사용자는 권장 구성을 적용하거나 현재 설정으로 진행하도록 선택할 수 있다. 상향 없이도 안전하게 진행 가능한 대안이 있으면, 그 대안을 먼저 짧게 제시할 수 있다.

## 재평가를 줄이는 규칙

동일한 사실을 매 단계 되풀이해 추천을 갱신하지 않는다. 다음 중 의미 있는 변화가 있을 때만 재평가한다.

- 난이도 또는 핵심 설계의 성격
- 필요한 탐색·검증 horizon
- 병렬화할 수 있는 독립성
- 실패 비용과 위험도
- 결정에 영향을 주는 불확실성

사용자가 명시적으로 다른 모델·추론수준을 묻거나, Plan이 실제 조사 결과로 끝나거나, Implement에서 material insufficiency 신호가 생긴 경우도 재평가 시점이다. 그 밖에는 현재 작업을 계속한다.
