# PR Review Response

PR에 작성된 코드 리뷰를 분석하고, 개발자가 각 리뷰의 의도와 수정 방향을 이해한 뒤 적절한 대응을 선택할 수 있도록 돕는다.

## Workflow

### 1. PR과 변경사항 파악

코드 리뷰를 분석하기 전에 다음 내용을 먼저 확인한다.

* PR의 목적
* 주요 변경사항
* 리뷰가 작성된 코드와 주변 맥락
* 기존 프로젝트 구조와 구현 방식

리뷰 코멘트만 독립적으로 해석하지 말고, 실제 코드와 변경 목적을 함께 고려한다.

---

### 2. 각 리뷰 내용 분석

각 코드 리뷰에 대해 다음 내용을 파악한다.

* 리뷰어가 지적한 문제
* 리뷰어가 기대하는 변경 방향
* 해당 문제가 발생하는 이유
* 현재 코드에 미치는 영향

리뷰 내용이 모호하거나 여러 의미로 해석될 수 있다면 하나의 의미로 단정하지 않는다.

가능성이 높은 해석을 설명하고, 필요한 경우 어떤 부분이 불명확한지도 알려준다.

---

### 3. 개발자가 이해할 수 있게 설명

각 리뷰를 단순히 재진술하지 말고 다음과 같이 설명한다.

* 현재 코드가 어떻게 동작하는지
* 리뷰어가 어떤 점을 문제로 보고 있는지
* 왜 수정이 필요할 수 있는지
* 수정하지 않을 경우 어떤 영향이 있는지

가능하면 실제 코드와 연결해서 설명한다.

지나치게 이론적인 설명보다는 현재 PR에서 왜 중요한지를 중심으로 설명한다.
위 설명과 이후 수정안 제안들은 md 문서로 남겨 개발자가 수시로 확인할 수 있게 하며
Agent 또한 이 문서를 참고하고, 진행에 따라 수정하여 업데이트한다.

---

### 4. 수정안 제안

각 리뷰에 대해 합리적인 수정 방법을 제안한다.
이때 각 리뷰에 대해 번호를 붙여 개발자가 지시하기 편하게 한다.

하나의 방법만 가능한 경우가 아니라면 여러 대안을 제시한다.

예:

#### 대안 A

수정 방법을 설명한다.

특징:

* 어떤 방식으로 문제를 해결하는지

장점:

* 해당 방식의 장점

단점:

* 해당 방식의 단점 또는 trade-off

#### 대안 B

동일한 방식으로 설명한다.

필요하다면 대안 C까지 제시할 수 있지만, 의미 없는 선택지를 만들기 위해 억지로 대안을 추가하지 않는다.

---

### 5. 권장안 제시

여러 대안 중 가장 적절하다고 판단되는 방법을 하나 추천한다.

권장 이유를 함께 설명한다.

판단할 때 다음 요소를 고려한다.

* 기존 프로젝트 구조와의 일관성
* 코드 복잡도
* 유지보수성
* 테스트 가능성
* 변경 범위
* 리뷰어가 지적한 문제를 실제로 해결하는지

단순히 "A를 추천한다"고 하지 말고, 왜 현재 상황에서 A가 가장 적합한지 설명한다.

---

### 6. 개발자의 선택을 기다린다

대안이 여러 개인 경우 개발자가 수정 방향을 선택할 수 있도록 한다.

개발자가 명확하게 선택하기 전에는 큰 구조 변경이나 의미 있는 설계 결정을 임의로 적용하지 않는다.

다만 다음과 같은 사소하고 명백한 변경은 별도의 선택지가 필요하지 않을 수 있다.

* 오타
* 명백한 import 정리
* 단순한 naming 수정
* 동작에 영향을 주지 않는 formatting

---

### 7. 선택된 수정안 적용

개발자가 선택한 방향에 따라 코드를 수정한다.

수정하면서 다음을 확인한다.

* 리뷰에서 지적한 문제가 해결되었는지
* 기존 동작이 의도치 않게 변경되지 않았는지
* 다른 코드와 일관성이 유지되는지

필요한 경우 관련 테스트를 수정하거나 추가한다.

---

### 8. 수정 결과 보고

수정 완료 후 다음 내용을 간단히 정리한다.

* 어떤 리뷰를 처리했는지
* 어떤 방식으로 수정했는지
* 변경된 주요 코드
* 실행한 테스트 또는 검증
* 아직 처리하지 않은 리뷰가 있는지

---

# Review Response Format

각 리뷰는 가능하면 다음 형태로 정리한다.

## Review

리뷰 내용을 요약한다.

## Interpretation

리뷰어가 무엇을 문제로 보고 있는지 설명한다.

현재 코드와 연결해서 개발자가 이해할 수 있도록 설명한다.

## Options

### A. 방법 이름

설명

장점:

* ...

단점:

* ...

### B. 방법 이름

설명

장점:

* ...

단점:

* ...

## Recommendation

추천하는 방법과 이유를 설명한다.

## Decision

개발자의 선택이 필요한 경우 선택을 요청한다.

# Guidelines

## 리뷰 자체도 검토한다

코드 리뷰가 항상 정답이라고 가정하지 않는다.

리뷰 내용이 현재 코드 구조와 맞지 않거나 불필요한 복잡도를 만드는 경우에는 그 이유를 설명한다.

필요하면 다음과 같이 판단할 수 있다.

* 리뷰대로 수정하는 것이 좋음
* 리뷰의 의도는 맞지만 다른 구현이 더 적절함
* 현재 구현을 유지하는 것이 더 합리적임
* 리뷰어에게 추가 확인이 필요함

리뷰를 무조건 수용하거나 무조건 반박하지 않는다.

---

## 기존 프로젝트 방식을 우선한다

일반적인 best practice보다 현재 프로젝트의 구조와 convention을 우선해서 판단한다.

비슷한 구현이 이미 존재한다면 가능한 한 기존 패턴과 일관성을 유지한다.

---

## 변경 범위를 불필요하게 확대하지 않는다

리뷰 대응 과정에서 직접 관련 없는 코드까지 리팩터링하지 않는다.

더 큰 개선이 필요해 보인다면 현재 리뷰 수정과 분리해서 제안한다.

---

## 리뷰 간 관계를 고려한다

여러 리뷰가 같은 원인에서 발생한 경우 각각 독립적으로 수정하지 말고 함께 해결할 수 있는지 검토한다.

반대로 서로 다른 문제를 하나의 큰 수정으로 묶지 않는다.

---

## 리뷰의 중요도를 구분한다

필요한 경우 리뷰를 대략 다음 수준으로 구분할 수 있다.

* 반드시 수정해야 하는 문제
* 수정이 권장되는 문제
* 설계 선택에 가까운 의견
* 스타일 또는 취향에 가까운 의견

단, 리뷰어의 의도를 임의로 왜곡하지 않는다.

---

# Avoid

* 리뷰 내용을 이해하지 않고 바로 코드부터 수정하는 것
* 하나의 수정 방법만 정답처럼 제시하는 것
* 의미 없는 대안을 억지로 만드는 것
* 개발자의 선택 없이 큰 설계 변경을 수행하는 것
* 리뷰와 관계없는 대규모 리팩터링
* 리뷰어의 의견을 무조건 옳다고 가정하는 것
* 프로젝트 맥락을 무시하고 일반적인 best practice만 적용하는 것
