# Git Checkpoint Development

전체 작업을 한꺼번에 구현한 뒤 변경사항만 여러 commit으로 나누지 않는다.
작업 단위는 구현 전에 정하고, 한 번에 하나의 작업 단위만 개발한다.

## 논리적 작업 단위

논리적 작업 단위는 독립적으로 설명하고 검토할 수 있는 작고 의미 있는 변경이다.
파일 개수만으로 단위를 나누거나, 서로 무관한 변경을 하나의 단위로 묶지 않는다.
하나의 기능도 여러 개의 독립적인 구현 단계로 나눌 수 있으면 분리한다.

각 단위는 가능하면 다음 조건을 만족하도록 정한다.

- 목적과 완료 조건이 명확하다.
- 변경 범위가 작아 개발자가 결과를 검토할 수 있다.
- 관련 테스트나 다른 합리적인 방법으로 검증할 수 있다.
- 다음 단위의 변경을 미리 포함하지 않는다.

## 진행 추적 문서

전체 작업을 추적하는 Markdown 문서를 하나 생성하고 작업이 끝날 때까지 같은 문서를 갱신한다.
다음 우선순위로 저장 위치를 정한다.

1. 프로젝트 루트에 기존 `docs/` 디렉터리가 있으면 그 안에 저장한다.
2. `docs/`가 없으면 프로젝트 지침, 기존 문서, 디렉터리 구조를 확인하여
   프로젝트가 실제로 사용하는 다른 문서 디렉터리에 저장한다.
3. 적절한 문서 디렉터리나 관례를 발견하지 못하면
   `.codex/checkpoints/<task-slug>.md`를 사용한다.

진행 문서만을 위해 프로젝트 루트에 새 `docs/`를 만들지 않는다.
선택한 문서 경로와 선택 근거를 작업 시작 시 사용자에게 알린다.

진행 문서는 기본적으로 작업 추적용이며 기능 commit에 포함하지 않는다.
사용자가 저장소에 문서를 함께 남기기를 명시적으로 요청한 경우에만 commit 대상으로 취급한다.

문서에 다음 내용을 유지한다.

- 전체 작업의 목적, 범위, 완료 조건
- 논리적 작업 단위 목록과 수행 순서
- 각 단위의 상태: `pending`, `in_progress`, `awaiting_approval`, `committed`
- 현재 단위의 목적과 완료 조건
- checkpoint별 주요 변경사항과 변경 파일
- 실행한 테스트와 결과
- 개발자의 승인, 수정 요청, 보류 등 결정 이력
- 적용된 commit message와 commit hash
- 계획 변경 사유, 미해결 질문, 다음 작업 단위

새로운 turn에서 작업을 계속할 때는 대화 내용에만 의존하지 말고 먼저 이 문서를 읽어
현재 단위, 승인 상태, 마지막 commit, 남은 작업을 확인한다.

## 실행 절차

### 1. 전체 작업 분석 및 분할

코드를 수정하기 전에 요청사항, 저장소 상태, 기존 변경사항을 확인한다.
전체 개발 범위를 작은 논리적 작업 단위로 나누고 수행 순서를 정한다.
진행 추적 문서를 생성하고 전체 계획과 첫 번째 단위를 기록한다.
첫 번째 단위 상태를 `in_progress`로 변경한다.
사용자에게 문서 경로, 전체 단위 목록, 이번에 수행할 첫 번째 단위를 알려준다.

작업을 진행하면서 새 정보가 발견되면 이후 단위의 계획은 조정할 수 있다.
계획을 조정하면 변경 내용과 사유를 진행 문서에 기록한다.
다만 현재 단위의 범위를 의미 있게 변경해야 한다면 먼저 문서를 갱신하고
사용자에게 설명한 뒤 판단을 요청한다.

### 2. 현재 단위 하나만 구현

현재 작업 단위에 필요한 변경만 구현한다.
후속 단위를 위한 코드, 리팩터링, 테스트를 미리 구현하지 않는다.

### 3. 변경사항 확인 및 검증

현재 단위와 관련 없는 변경이 포함되지 않았는지 확인하고 관련 테스트를 실행한다.
검증이 실패하면 현재 단위 안에서 원인을 해결하고 다시 검증한다.
검증 실패 상태에서는 checkpoint 승인이나 commit을 요청하지 않는다.

### 4. Checkpoint에서 반드시 중단

현재 단위의 구현과 검증이 끝나면 즉시 개발을 중단한다.
다음 작업 단위를 시작하거나 관련 파일을 수정하지 않는다.

진행 문서의 현재 단위 상태를 `awaiting_approval`로 바꾸고 다음 내용을 기록한다.

- 전체 진행 상황과 현재 완료한 작업 단위
- 주요 변경사항
- 변경된 파일
- 실행한 테스트와 결과
- 남아 있는 작업 단위
- 제안하는 commit message

갱신한 문서를 기준으로 같은 내용을 사용자에게 보고한 뒤 승인 또는 수정 지시를 기다린다.
보고에 진행 문서 경로를 포함한다.
사용자가 명확하게 응답하기 전에는 commit하거나 다음 단위를 개발하지 않는다.

### 5. 승인 또는 수정 처리

사용자의 결정을 먼저 진행 문서에 기록한다.

사용자가 수정을 요청하면 현재 단위 상태를 `in_progress`로 되돌리고 현재 작업 단위만 수정한다.
다시 검증한 뒤 문서를 갱신하고 새로운 checkpoint를 보고한다.

사용자가 승인하면 현재 단위와 관련된 파일만 stage하고 commit한다.
Conventional Commits 형식을 사용하고, 메시지는 가능한 한 한글로 작성한다.
클래스명이나 외래어 등을 억지로 번역하지 않는다.

예:

- `feat: 문서 추가`
- `fix: 토큰 중복 제거`
- `refactor: 권한 Validator 권한 충돌 수정`

### 6. 다음 단위로 진행

승인된 단위의 commit이 성공한 뒤에만 다음 작업 단위 하나를 시작한다.
commit 직후 진행 문서에 해당 단위의 상태를 `committed`로 바꾸고
실제 commit message와 commit hash를 기록한다.

남은 단위가 있으면 다음 단위 상태를 `in_progress`로 바꾸고 현재 단위로 표시한다.
다음 단위를 구현하고 검증한 뒤 다시 checkpoint에서 중단한다.
모든 작업 단위가 완료될 때까지 2~6단계를 반복한다.

마지막 단위가 승인되어 commit되면 진행 문서를 최종 상태로 갱신하고
전체 작업 완료, 최종 검증 결과, 진행 문서 경로를 보고한다.

## 경계 위반 처리

실수로 여러 작업 단위를 미리 구현했으면 변경사항을 사후에 commit 단위로만 나누지 않는다.
즉시 개발을 중단하고 어떤 checkpoint 경계를 넘었는지 사용자에게 보고한 뒤 처리 방향을 요청한다.

## 금지

- 여러 작업 단위를 먼저 구현한 뒤 commit만 분리
- 현재 checkpoint 승인 전 다음 작업 단위 개발
- 승인 전 commit
- checkpoint에서 진행 문서를 갱신하지 않고 보고
- 사용자의 명시적 요청 없이 진행 문서를 기능 commit에 포함
- main 브랜치 직접 commit
- force push
- 테스트 실패 상태 commit
- 관련 없는 변경을 같은 commit에 포함
